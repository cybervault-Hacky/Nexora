# Phase 3 — Mini Local Image Generation

Phase 3 adds a backend-only local text-to-image path. It does not change the chat composer or add a screen. Image generation remains separate from the Mini/Sonnet coding-model registry and process.

## Selected model and provenance

- **Model:** Stability AI SD-Turbo, distilled from Stable Diffusion 2.1 using Adversarial Diffusion Distillation.
- **Publisher/model card:** <https://huggingface.co/stabilityai/sd-turbo>
- **Pinned weight revision:** `9fee4496504b3b0e95e11c80bdf0fb0c7a5d4aa8`
- **File:** `sd_turbo.safetensors`, exactly `5,214,561,328` bytes; publisher Xet/LFS pointer SHA-256 `3f067a1b943cf162f2b8f8588f6cf5824bd5b4c7d1d88d87164b9ca123616549`.
- **License:** Stability AI Community License, dated 2024-07-05. Commercial-purpose use requires registration with Stability AI; the license requires an enterprise license above USD 1,000,000 annual revenue. The acceptable-use policy, restrictions, attribution, and redistribution terms apply. Nexora does not redistribute or bundle the weights; the existing manager downloads them from the pinned publisher URL.
- **Resource disclosure:** the model card documents 512×512 as preferred and one-to-four denoising steps; it does not publish a reliable RAM/VRAM minimum for this CPU runtime path. The registered RAM/VRAM requirements therefore remain unknown. The exact raw checkpoint size is used only as a lower-bound screening check, not as a sufficient-memory claim.

## Runtime adapter

The adapter targets upstream [`stable-diffusion.cpp`](https://github.com/leejet/stable-diffusion.cpp), whose project documentation lists SD-Turbo, safetensors, Windows, CPU, and the CLI text-to-image interface. If native admission and later preflight permit a request, the app forces `--backend cpu`; it does not infer or silently use CUDA, Vulkan, DirectML, or cloud inference. The implemented path is designed to start a local CLI process per admitted request, load the validated checkpoint, create a PNG, and exit; process exit releases runtime/model resources (there is no persistent warm model session or separate load/unload command in this phase). Current admission prevents a request from reaching this execution path.

The runtime executable is discovered only at fixed application-resource locations (`image-runtime/sd-cli[.exe]` or `binaries/sd-cli[.exe]`), never from `PATH`, a project working directory, or a renderer-supplied path. The status command checks that the runtime reports a CPU backend. Nexora does not download or bundle an executable in this change.

**Current blocker:** this repository has no stable-diffusion.cpp executable/DLL bundle, package resource declaration, or pinned, checksummed upstream runtime release. Runtime presence in any particular installation is not established by this source configuration and was not queried here; the adapter only resolves executables from the fixed application-resource locations above. Model/runtime compatibility remains unconfirmed. More importantly, current shared admission supplies runtime availability/compatibility as unknown and the complete CPU working-memory requirement remains unknown, so a request with validated assets is denied before runtime resolution/probing or checkpoint hashing. Actual generation remains unavailable until a reviewed CPU runtime build and its provenance/version are established and a later authorized validation clears the runtime/model and model-specific resource evidence; no generation success is simulated.

> **Phase 11 follow-up:** `generate_local_image` now consults the shared media-resource admission boundary before runtime probing or large model-file hashing. When the manager reports validated assets, current admission remains unknown because runtime availability/compatibility and model-specific system-memory requirements are not established; if assets are missing or unvalidated, admission is unavailable. No generation process is started on either result. The existing `canAttemptGeneration` status field now previews the same admission policy, but it is not a reservation, does not guarantee that a later request will be admitted, and does not imply capability usability. **Current execution order:** shared admission runs before runtime discovery/probing, asset revalidation, or checkpoint hashing. Because runtime availability/version/compatibility and the complete memory requirement are unresolved, a request with validated assets currently stops at `Unknown`; absent or invalid assets stop at `Unavailable`. The lower-level runtime, model-lock, and output safeguards described below remain implemented for a future admitted execution path, but are not reached in the current source configuration.

## Request, resources, cancellation, and output

- The backend accepts a trimmed nonempty prompt up to 2,000 Unicode characters/8 KiB and rejects control characters. Output is fixed at 512×512 PNG. Light/Balanced/Quality map to one/two/four steps; CFG is fixed at `0.0` as prescribed by the model card. The optional seed is an unsigned 32-bit integer; otherwise a secure random seed is generated.
- The Phase 11 shared gate runs first using a Phase 1 resource snapshot and Phase 2 lifecycle record. It applies the registered raw-checkpoint-size screening floor and output-volume reserve, while keeping complete working-memory requirements unknown. If admission is ever cleared, the downstream path resolves and probes the located CLI, invokes the Phase 2 validator, then verifies/locks the checkpoint against the trusted digest before process start. Passing any of these checks is only eligibility to attempt generation; it is not proof of sufficient memory or compatibility. Under current evidence, the gate denies before runtime probing, validation, or checkpoint hashing, so these downstream checks are not reached.
- If a request reaches the worker, only one generation may run at a time. The operation lock prevents model removal/replacement while inference reads the checkpoint. Cancellation sets a native flag, kills and reaps the local child, and discards request-scoped staging output; window/app shutdown requests the same cancellation. A one-hour time limit and 64 MiB artifact cap are enforced in the execution path. The runtime does not provide structured step progress, so status reports preparation/running/cancelling only and no percentage. These safeguards have not been exercised in Phase 12.
- The intended output staging and final files are under app data `generated-images/`, separate from model weights. An admitted request uses a cryptographically random ID and exclusive staging folder. The source path publishes without replacement only after successful runtime exit, PNG chunk framing/CRCs/dimensions/end marker validation, bounded RGB/RGBA pixel decoding, and hashing. Metadata records model ID/revision, backend, profile, steps, seed, dimensions, MIME type, size, SHA-256, and timestamp. Renderer retrieval accepts only the opaque artifact ID, not an arbitrary path. This output path exists in source but has not been reached or verified in the current admission state.

## IPC

Added commands: `get_local_image_generation_status`, `generate_local_image`, `cancel_local_image_generation`, and `get_generated_image_artifact`. TypeScript wrappers are in `ui/src/lib/imageGeneration.ts`; no visible UI consumes them in this phase. The generation command never calls the coding LLM and never falls back to a cloud service.

## Capability status

Implemented in source: pinned SD-Turbo registry entry and trusted download metadata; Phase 2 download/validation reuse; CPU-only CLI adapter boundary; request validation; adaptive resource checks; exclusive generation/cancellation state; child process supervision; PNG verification and application-owned artifact metadata; typed Tauri/TypeScript contracts.

Unavailable or unverified: bundled inference runtime, runtime release pin/checksum, guaranteed model/runtime compatibility, published exact RAM requirement, GPU acceleration, actual generated output, and Windows execution validation. Builds and tests were not run in this phase per the verification restriction.
