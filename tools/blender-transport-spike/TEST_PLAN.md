# Windows + Blender transport feasibility test plan

**Status:** specification only. No transport harness is included, so every Windows pipe, identity, protocol, lifecycle, and real Blender test below is currently `BLOCKED`. Do not change a case to `PASS` from preflight output, documentation, a mock, or a test in another language/process pair.

Before running these cases, obtain separate authorization for a disposable, non-production Rust server and a user-enabled Blender test client. The POC must include its own pinned build/run/cleanup instructions. It must use a health-check-only, bounded, versioned protocol and explicit timeouts; it must not launch Blender, install an add-on, expose a listener, access credentials, run arbitrary code, inspect/edit/save scenes, or integrate with Nexora UI/installer. Until the harness's actual transport, ACL, framing, challenge, peer identity, and key-handling decisions are reviewed, these cases are test requirements rather than commands to execute.

## Status vocabulary

- `PASS`: the stated behavior was observed with the actual Windows/Rust/Blender test peers and the evidence required below is attached.
- `FAIL`: observed behavior violates the expected safe outcome, or required evidence is absent/mismatched after a test was attempted.
- `BLOCKED`: required host, tool, account/session, test harness, or real Blender runtime is unavailable. State the blocker; do not infer a pass.
- `NOT_RUN`: test is ready but not attempted. Keep separate from `BLOCKED`.

Preflight may report prerequisites detected; that status is not one of the pipe-test outcomes and never turns a transport case into `PASS`.

## Execution order and evidence rules

1. Start with `PRE-01`, then `PRE-02`. Stop if required runtime prerequisites are missing.
2. Before any pipe test, review and record the POC's exact source revision, artifact hashes, ACL, pipe name/lifetime, maximum frame size, challenge/key policy, peer identity checks, and finite timeouts. Do not test an unreviewed or production-connected binary.
3. Run the positive identity/health path once, then each negative case independently. Reset the disposable VM when needed. Repeat endpoint race and duplicate-client cases and record counts/timings.
4. Run Blender compatibility/lifecycle cases for every exact candidate version. Use a manually started Blender build and a disposable project/session; never use an important user scene.
5. Complete [`result-template.json`](result-template.json), keep logs local, and attach only redacted evidence. Record blocked cases with the concrete missing prerequisite; do not silently omit them.
6. Preserve Phase 5A's `NO-GO FOR PRODUCTION` decision until a separate review considers real Windows + Blender results, both-direction identity, access-control evidence, and residual same-user/key risks. Preflight/static results cannot authorize production.
